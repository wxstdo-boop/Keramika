# Релизы

## Версионирование

Версия живёт в одном месте — `pubspec.yaml`:

```yaml
version: 1.6.49+45121
#           │      └── versionCode
#           └───────── versionName
```

`versionName` видит пользователь, `versionCode` — система, и она обязана
расти с каждым релизом.

### Главное правило: versionCode строго выше, чем на телефоне

Flutter прибавляет к номеру из `pubspec.yaml` индекс ABI для split-APK:

| ABI | Прибавка | Итог при `45121` |
|---|---|---|
| `armeabi-v7a` | +1000 | 46121 |
| `arm64-v8a` | +2000 | **47121** |
| `x86_64` | +3000 | 48121 |

Поэтому «на телефоне 47120» означает: базовый номер следующего релиза должен
быть **45122 или выше**. Ниже — `adb install -r` упадёт с
`INSTALL_FAILED_VERSION_DOWNGRADE`, и обновление поверх старой версии
невозможно (а вместе с ним — перенос PIN, будильников и всей статистики).

Универсальная проверка: базовый номер должен превышать максимум из
`базовый номер на устройстве` и `versionCode соседних ABI минус их прибавка`.
Проще всего — просто брать следующий круглый шаг и не переиспользовать номера.

## Порядок выпуска

### 1. Подготовка

```bash
flutter pub get
flutter analyze          # должно быть "No issues found!"
flutter test
```

Проверить, что в индекс не попал мусор:

```bash
git status --short
```

### 2. Коммит и тег

Версию в `pubspec.yaml` нужно поднять **до** коммита.

```bash
# 1. Правим version в pubspec.yaml
# 2. Коммитим
git add pubspec.yaml
git commit -m "Подготовить v1.6.50+45122"

# 3. Тег в формате v<versionName>+<versionCode>
git tag v1.6.50+45122

# 4. Пушим ветку и тег
git push origin main
git push origin v1.6.50+45122
```

### 3. Сборка в CI

Схема workflows:

| Workflow | Когда срабатывает | Что делает |
|---|---|---|
| `ci.yml` | push в `main`, pull request | `analyze` + `test` |
| `ship.yml` | push в `main` (по paths-фильтру) или вручную | поднимает версию, коммитит и зовёт общий процесс сборки |
| `release-on-tag.yml` | push тега `v*` | разбирает тег и зовёт общий процесс сборки |
| `release.yml` | **только** как переиспользуемый (`workflow_call`) | единственное место, где собирается и публикуется APK |

Сборка живёт **в одном файле** — `release.yml`. `ship.yml` и
`release-on-tag.yml` только вызывают его через `uses:` и своих шагов сборки
не содержат. Так публикуемый APK гарантированно собран тем же SDK, тем же
lockfile и после тех же проверок, что и CI. Раньше сборок было две, и они
разъехались: тег-сборка не проверяла lockfile, не гоняла тесты и брала
плавающий `channel: stable` вместо зафиксированной версии Flutter.

Общий процесс сборки (`release.yml`) делает по шагам:

1. применяет версию к `pubspec.yaml`;
2. `flutter pub get --enforce-lockfile` — релиз собирается ровно с теми
   зависимостями, что зафиксированы в репозитории;
3. `flutter analyze` и `flutter test --concurrency=1`;
4. достаёт keystore из секретов и пишет `android/key.properties`;
5. поднимает память Gradle до 4 ГБ (только в CI);
6. собирает `flutter build apk --release --split-per-abi`;
7. переименовывает ассеты в `Keramika-<версия>-<abi>.apk`;
8. считает SHA-256 каждого ассета и кладёт таблицу в тело релиза;
9. публикует GitHub Release.

Flutter зафиксирован на `3.47.5` — той же версии, что и в `ci.yml`.
Плавающий `channel: stable` означал бы, что релиз может собраться на
непротестированной версии SDK.

Таблица SHA-256 в теле релиза обязательна: приложение сверяет скачанный
файл именно с ней (`digest` ассета GitHub) и отменяет обновление, если
хеша нет.

Имя ассета содержит версию, поэтому приложение может выбрать свой ABI при
автообновлении (`lib/services/update_service.dart` парсит его из ссылки).

### Секреты репозитория (нужны для подписи)

Сборка релиза не пройдёт без четырёх секретов GitHub
(Settings → Secrets and variables → Actions → Repository secrets):

| Секрет | Что это |
|---|---|
| `KEYSTORE_BASE64` | сам keystore, закодированный в base64 |
| `STORE_PASSWORD` | пароль хранилища |
| `KEY_PASSWORD` | пароль ключа |
| `KEY_ALIAS` | alias ключа внутри хранилища |

`KEYSTORE_BASE64` собирается так (одной строкой, без переносов):

```bash
base64 -w0 android/app/keramika-release.jks
```

Если `KEYSTORE_BASE64` пуст или в него попал не base64, workflow теперь падает
сразу с внятным сообщением. Раньше это выглядело как загадочное

```
KeytoolException: Failed to read key  from store ".../keystore.jks":
Tag number over 30 is not supported
```

на этапе `:app:packageRelease` — падал разбор пустого файла, а не Gradle.

### 4. Проверка релиза

Приложение само проверяет GitHub Releases и предлагает обновление:

- сверяется `versionCode` — обновление предлагается только если он выше;
- скачанный APK сверяется по **SHA-256**, взятому из описания релиза;
- ставится поверх старого, данные сохраняются.

Это значит, что в описании релиза **обязательно** должны быть SHA-256 суммы
каждого ассета, иначе обновление не пройдёт проверку. Если workflow не
проставляет их автоматически — дописать вручную при публикации.

## Откат

Откатить можно только публикацию, а не установленный APK:

```bash
# Удалить тег с GitHub
git push origin --delete v1.6.50+45122
```

APK, уже установленный у пользователя, откатить нельзя. Поэтому перед
публикацией стоит прогнать сборку локально на реальном устройстве.

## Чек-лист перед релизом

- [ ] `versionCode` в `pubspec.yaml` выше, чем на устройстве
- [ ] `flutter analyze` чист
- [ ] `flutter test` зелёный
- [ ] Заметки в `lib/screens/changelog_screen.dart` дополнены
- [ ] `git status` без мусора и случайных файлов
- [ ] Сборка установлена на реальный телефон поверх старой версии
- [ ] Будильник срабатывает после перезагрузки
- [ ] SHA-256 суммы попали в описание релиза
